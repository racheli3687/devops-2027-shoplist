# שיעור 5 — שיעורי בית

## חלק א — מפת ה-cluster

| רכיב | איפה הוא רץ | מה הוא עושה, במשפט אחד | אנלוגיה |
|---|---|---|---|
| API server | הנהלה | הדלת היחידה של ה-cluster: כל פקודה מ-kubectl נכנסת דרכו, והוא בודק אותה ומעביר הלאה. | פקיד הקבלה בקונדיטוריה, שכל ההזמנות עוברות דרכו |
| etcd | הנהלה | מסד הנתונים של ה-cluster: שומר מה אנחנו רוצים שיהיה ומה קיים עכשיו. | המחברת הגדולה של ההזמנות והמלאי |
| scheduler | הנהלה | בוחר על איזה node ירוץ כל pod חדש, לפי המקום הפנוי. הוא רק מחליט, לא מריץ. | מי שמחלק את ההזמנות בין המטבחים |
| controller manager | הנהלה | בודק כל הזמן אם מה שקיים שווה למה שביקשנו, ואם לא, מתקן. | מנהל משמרת שמוודא שבוויטרינה יש בדיוק מה שהוזמן |
| kubelet | כל node | מקבל מההנהלה הוראה אילו pods צריכים לרוץ אצלו, דואג שירוצו, ומדווח אם הכל בסדר. | מנהל המטבח שמבצע את ההזמנות ומדווח להנהלה |
| container runtime | כל node | התוכנה שמפעילה בפועל את ה-containers מתוך ה-images. | התנור והאופה שמכינים את העוגה בפועל |
| kube-proxy | כל node | דואג שפנייה ל-Service תגיע לאחד ה-pods שמאחוריו, ומחלק בין כמה pods. | מארחת בכניסה שמפנה כל אורח לשולחן פנוי |
| coredns | pod ב-cluster, ב-namespace בשם kube-system | מתרגם שם של Service (כמו `greeter`) לכתובת שאפשר להגיע אליה. זה המימוש של הרעיון משיעור 4: אפשר לפנות לשירות לפי שם ולא לפי כתובת IP. | ספר הטלפונים של הקונדיטוריה: מחפשים שם ומקבלים מספר |

## חלק ב — תרחישים

### 1. scale

הפקודה מגיעה ל-API server, שבודק אותה ושומר ב-etcd שעכשיו רוצים 4 pods. ה-controller manager שם לב שיש פער (יש 2, רוצים 4) ויוצר שני pods חדשים, עדיין בלי node. ה-scheduler בוחר לכל pod חדש node מתאים. ה-kubelet באותו node מקבל את ההוראה, וה-container runtime מפעיל את ה-containers. בסוף ה-kubelet מדווח ל-API server שה-pods ב-Running, וזה נשמר ב-etcd.

### 2. שלוש בלילה

כשה-container של backend קורס, ה-kubelet שעל ה-node שם לב לזה ומפעיל אותו מחדש דרך ה-container runtime. ה-pod נשאר אותו pod, ורק ה-container שבתוכו עולה מחדש, בלי שאף אחד צריך לקום באמצע הלילה. אם מישהי מוחקת את ה-pod כולו, ה-controller manager שם לב שיש פחות pods ממה שביקשנו, ויוצר pod חדש. ה-scheduler בוחר לו node, וה-kubelet וה-container runtime מפעילים אותו שם.

### 3. node נכבה

ב-cluster בענן, ה-pods שרצו על node 2 נעלמים יחד איתו. ה-controller manager שם לב שיש פחות pods ממה שביקשנו, ויוצר pods חדשים. ה-scheduler בוחר להם nodes, והם עולים על שני ה-nodes שנשארו, כך שהאפליקציה ממשיכה לעבוד. ב-cluster של Docker Desktop בכיתה יש node אחד בלבד, שמריץ גם את ההנהלה וגם את ה-pods. לכן אם המחשב נכבה, אין node אחר שיכול להרים את ה-pods, והכל נעצר.

### 4. מהכיתה לענן

שני דברים בקבצי ה-YAML לא יעבדו ב-EKS. ראשית, `imagePullPolicy: Never` אומר ל-Kubernetes להשתמש רק ב-image שנמצא על ה-node עצמו. בכיתה ה-image נמצא על המחשב שלי, אבל ב-EKS ה-nodes הם מחשבים בענן ואין עליהם את ה-images שבניתי, ולכן ה-pods ייכשלו (`ErrImageNeverPull`). צריך לדחוף את ה-images ל-registry בענן (למשל ECR של אמזון), לכתוב ב-YAML את הכתובת המלאה שלהם, ולשנות את `imagePullPolicy` ל-`IfNotPresent` או `Always`. שנית, Service מסוג `NodePort` פותח דלת בפורט 30090, שמתאימה ל-`localhost` על המחשב שלי, אבל ללקוחות אמיתיים באינטרנט אין דרך להגיע אליה בנוחות. צריך לשנות ל-`type: LoadBalancer`, שמבקש מהענן כתובת חיצונית וחלוקת עומסים אוטומטית.

### 5. pod בודד

כשיצרתי pod עם `kubectl run`, זה היה pod בודד, ואף אחד לא אחראי להחזיר אותו. כשמחקתי אותו, הוא נעלם ולא חזר, כי לא הייתה שום "הזמנה קבועה" שדורשת שהוא יהיה קיים. ה-pods של `web`, לעומת זאת, נוצרו על ידי Deployment, שמחזיק את ההזמנה: "תמיד צריכים להיות כך וכך pods". כשמחקתי pod של `web`, ה-controller manager שם לב שיש פחות pods ממה שה-Deployment דורש, ויצר אחד חדש. כדי ש-`stats` יחזור תמיד, הייתי יוצרת עבורו Deployment (במקום `kubectl run`) עם `replicas: 1`. כך אם ה-pod יימחק או ייפול, ה-Deployment יחזיר אותו.
